## 一、这次要做什么

需求原文（六条）：

1. **配置检查**：检查 `.env`、`.env.example`、配置文件及 Docker Compose 配置，
   识别必需配置缺失、环境变量未配置、配置引用不一致、明显格式错误等问题。
   **禁止输出真实密钥**。
2. **启动问题分析**：结合配置检查结果及已有健康检查、日志分析能力，分析常见启动失败原因，
   例如端口冲突、配置缺失、依赖服务不可用、数据库连接失败、镜像或启动配置异常。
3. **诊断报告**：中文输出问题摘要、证据、可能原因和处理建议；
   **严格区分已证实事实与推测，不得编造检查结果**。
4. **安全限制**：默认只读，不自动修改配置、不执行启动或重启操作；
   限制可访问的项目路径，防止路径穿越，并对密码、Token、API Key 等敏感信息脱敏。
5. **集成与测试**：按现有架构注册工具、更新提示词；新增 pytest 测试，覆盖正常配置、
   配置缺失、格式错误、敏感信息脱敏、路径安全及异常处理。**确保前两个魔改的测试全部通过**。
6. **文档**：本文件。

## 二、整体设计

### 2.1 为什么是两个工具而不是一个

需求里的第 1 条和第 2 条，输入完全不同：

| | 第 1 条 配置检查 | 第 2 条 启动问题分析 |
|---|---|---|
| 数据来源 | 项目目录里的**文件** | **Docker 实际状态** + 配置文件 |
| 需要 Docker 吗 | 不需要 | 需要 |
| 能离线跑吗 | 能 | 不能 |
| 回答的问题 | "配置写得对吗" | "为什么起不来" |

硬塞进一个工具会有两个后果：没有 Docker socket 的环境连配置都查不了；
以及一个函数里混着文件 I/O 和网络 I/O，没法单独测。

所以拆成：

```
check_config      同步，只读文件        → 配置本身有没有问题
diagnose_startup  异步，文件 + Docker   → 配置说该跑什么，Docker 实际在跑什么
```

两个工具**共用同一套配置分析逻辑**（`config_check.audit()`），
所以"配置类结论"在两边是一模一样的措辞，不会出现同一个问题两种说法。

### 2.2 分工边界：不重复造已有的轮子

前两个魔改已经有 `check_project`（目录结构）、`check_docker`（容器列表）、
`check_service`（接口探活）、`check_container_logs`（日志分析）。
新工具的做法是**明确引用它们，而不是重新实现**：

- `diagnose_startup` 发现"容器已退出，退出码 137"之后，
  报告末尾直接写"用 `check_container_logs` 读它的日志 —— 退出码只能说明**怎么死的**，
  日志才能说明**为什么死**"。
- 报告里显式声明"**未检查**"清单（4 项），其中一条就是
  "运行中的容器实际拿到了什么环境变量（只读文件，不 exec 进容器）"，
  并写明"配置检查通过 ≠ 服务健康，那要用 `check_service`"。

这个设计来自第二个魔改的教训：工具报告最危险的失败模式不是漏报，
而是**让模型把"没查"当成"查过了没问题"**。

### 2.3 架构：纯函数内核 + 命令式外壳

沿用了第二个魔改里 `log_analysis.py` 的结构：

```
config_check.py   ← 纯函数，零 I/O、零 app.* 依赖，输入是字符串，输出是结论对象
      ▲
      │ audit() / check_startup()
      │
ops.py            ← 外壳：路径安全校验、读文件、连 Docker、渲染报告
```

好处很直接：`config_check.py` 的测试全部是"喂一段字符串，断言结论"，
不需要临时目录、不需要假 Docker，单个测试毫秒级。
而 `ops.py` 那边测的是安全策略和 I/O 边界，职责分明。

### 2.4 文件结构

```
backend/app/agents/tools/
├── config_check.py   （新，1433 行）纯配置/启动分析引擎
├── ops.py            （改，945 → 2069 行）新增 check_config / diagnose_startup

```

## 三、实现原理

### 3.1 配置检查：`audit()`

签名（全部是纯数据，不做 I/O）：

```python
def audit(
    *,
    dotenv_files: Mapping[str, str],    # 相对路径 -> .env 原文
    compose_files: Mapping[str, str],   # 相对路径 -> compose 原文
    present_files: Collection[str] = (),# 目录下实际存在的条目
    required_keys: Sequence[str] = (),  # 运维声明的必需变量
    gitignore: str = "",
) -> list[ConfigFinding]
```

一共 **10 类检查**，都在 `_CONFIG_CHECKED_ITEMS` 里逐条列给用户看：

| # | 检查 | 命中时的分类 | 级别 |
|---|---|---|---|
| ① | `.env` 语法（无等号的行、非法键名、重复键、空值） | 配置格式错误 / 重复定义 | 严重 / 警告 |
| ② | `.env.example` 声明了但 `.env` 里没有 | 必需配置缺失 | 严重 |
| ③ | `.env` 里有但模板里没有 | 配置未在模板中记录 | 提示 |
| ④ | 模板文件里写入了真实密钥 | 模板文件含真实密钥 | 严重 |
| ⑤ | compose YAML 语法 / services 段 / 服务缺 image+build | Compose 配置错误 等 | 严重 |
| ⑥ | compose 引用的 `env_file` 不存在 | Compose 引用的配置文件不存在 | 严重 |
| ⑦ | `depends_on` 指向不存在的服务 | 依赖的服务不存在 | 严重 |
| ⑧ | 两个服务抢同一个宿主机端口 | 宿主机端口冲突 | 严重 |
| ⑨ | `${VAR}` 无默认值且没定义 | Compose 变量未定义 | 警告 |
| ⑩ | `.env` 没被 `.gitignore` 覆盖 | 实际配置未加入忽略列表 | 警告 |

#### 关键设计 1：dotenv 解析"拆不开就说拆不开"

`parse_dotenv()` 支持 `export KEY=value`、单双引号、行内 `#` 注释。
但遇到**引号不闭合**这类情况时只记录问题、**不猜**：

```python
if value[:1] in ("'", '"'):
    problems.append(f"第 {number} 行 {key} 的值引号没有闭合，解析结果可能不是预期的。")
```

因为"猜"出来的值会变成一条看起来很像事实的假证据。

#### 关键设计 2：`yaml.safe_load` 而不是 `yaml.load`

```python
data = yaml.safe_load(text)
except yaml.YAMLError as exc:
    mark = getattr(exc, "problem_mark", None)
    where = f"第 {mark.line + 1} 行第 {mark.column + 1} 列" if mark else "位置未知"
```

compose 文件是**被检查的对象**，可能是别人写的，属于不可信输入。
`yaml.load` 允许文件里构造任意 Python 对象（`!!python/object/apply:os.system`），
等于把 RCE 递给对方。`safe_load` 遇到这种标签直接报错。

这条有专门的测试用例，断言"报错而不是执行"：

```python
def test_parse_compose_does_not_construct_arbitrary_objects():
    parsed = cc.parse_compose("services: !!python/object/apply:os.system ['echo hi']\n")
    assert parsed.services == {}
    assert parsed.problems  # 报错，而不是执行
```

另外一个细节：解析失败时从 `problem_mark` 里**取出具体行列号**放进证据。
"YAML 语法错误"和"第 7 行第 3 列附近有语法错误"对使用者来说是两回事。

### 3.2 脱敏：两层独立保险

需求写的是"禁止输出真实密钥"，这条要做成**结构性保证**而不是"记得别打印"。

**第一层在数据层**（`DotenvFile.safe_items()`）：

```python
def safe_items(self) -> list[tuple[str, str]]:
    """只返回可以安全展示的 (键, 值)。
    密钥类的键，值一律换成 "***" —— 这样即使调用方想打印，也打印不出真东西。
    """
    for key in self.order:
        value = self.values.get(key, "")
        if is_sensitive_key(key):
            out.append((key, "***" if value else ""))
```

`DotenvFile.values` 里确实存着真值（要用来判断"是不是占位符"），
但**渲染路径只能走 `safe_items()`**。

**第二层在渲染层**：`_preview_config_values()` 对每个值再过一遍 `_redact()`（复用第一个魔改的脱敏函数），
两道保险互不依赖。

**密钥判定用分段匹配**，不是子串匹配：

```python
_SENSITIVE_WORDS = {AUTH, AUTHORIZATION, BEARER, CREDENTIAL(S), DSN, KEY, KEYS,
                    PASSWD, PASSWORD(S), PRIVATE, PWD, SALT, SECRET(S), TOKEN(S)}
```

键名按 `[^A-Za-z0-9]+` 切成段再和这个集合求交集。
所以 `JWT_SECRET_KEY` 命中，而 `MONKEY_COUNT`（切成 `MONKEY`+`COUNT`）不命中，
`KEYSTONE_URL` 也不命中 —— 用子串匹配的话这两个会天天误报。

**报告里只给键名和长度**：

```
backend/.env.example：API_KEY_ENCRYPTION_KEY 填的是具体值而不是占位符（长度 26，值已隐藏）
```

连前几位都不给（`sk-abc…` 这种前缀有时候本身就有信息量）。

### 3.3 真实密钥 vs 占位符：怎么区分

模板文件（`.env.example`）里出现具体值要报警，但 `changeme`、`your-api-key-here`
这类占位符不能报 —— 否则每个正常项目都在报警，报警就没意义了。

两档判断：

```python
_PLACEHOLDER_HINTS = ("<", "***", "...", "change-this", "change_me", "change-me",
                      "changeme", "dummy", "example", "fake", "none", "null",
                      "placeholder", "redacted", "replace-me", "sample",
                      "sometoken", "todo", "your-", "your_", "yourkey")

_REAL_SECRET_RE = re.compile(
    r"^(?:sk-[A-Za-z0-9_-]{16,}|sk_live_…|rk_live_…|lsv2_…|tvly-…|ghp_…|"
    r"github_pat_…|glpat-…|AKIA[0-9A-Z]{16}|xox[baprs]-…|eyJ….….…)"
)
```

- 命中 `_REAL_SECRET_RE` → **严重**「模板文件含真实密钥」：这是云平台签发的真实格式。
- 不像占位符但也不匹配任何已知格式 → **警告**「模板文件写入具体密钥值」。
- 像占位符 → 不报。

**在真实的 AgentHub 仓库上实测**，这条精准命中了：

```
backend/.env.example：API_KEY_ENCRYPTION_KEY 填的是具体值而不是占位符（长度 26，值已隐藏）
backend/.env.example：POSTGRES_PASSWORD 填的是具体值而不是占位符（长度 9，值已隐藏）
```

而 `JWT_SECRET_KEY`（填的是形如 `your-<用途>-change-this-in-production` 的占位符）没被报 —— 判定正确。

### 3.4 启动问题分析：`check_startup()`

核心思路一句话：**配置说"应该跑什么"，Docker 说"实际在跑什么"，差集就是启动出问题的地方。**

```python
def check_startup(compose, containers, *, inspect=None) -> list[ConfigFinding]
```

`containers` 是真实的 `GET /containers/json?all=1` 返回（含已停止容器），
`inspect` 是 `容器名 -> GET /containers/{id}/json` 返回，用来补退出码。

**第一步是"把 compose 服务和容器对上"**，这里有三种办法，按可靠性从高到低：

```python
def match_container(service, containers):
    # 1. container_name 完全一致（compose 里写死了名字，最准）
    # 2. compose 打的标签 com.docker.compose.service
    # 3. 容器名 == 服务名，或形如 <项目>-<服务>-1 / <项目>_<服务>_1
    pattern = re.compile(rf"^(?:.*[-_])?{re.escape(service.name)}[-_]1$")
```

第 3 条的正则是关键：compose 默认生成的容器名是 `<项目名>-<服务名>-1`，
而项目名由目录名决定，工具事先不知道。正则用 `(?:.*[-_])?` 把未知的项目名吃掉。

**找不到就返回 `None`，报告里说"容器不存在"，但不写"服务一定没启动"** ——
这个 compose 可能根本没在管这台机器上的容器：

```python
"容器根本不存在，说明这个服务没有被创建过 —— 可能是从来没启动过，"
"也可能是被 `docker compose down` 删掉了。"
```

#### 退出码：只给线索，不给结论

```python
_EXIT_CODE_HINTS = {
    137: "被 SIGKILL 强制杀死：最常见的原因是内存超限（OOM），也可能是 docker stop 超时后升级成强杀。",
    143: "收到 SIGTERM 后退出：属于正常停止流程（docker stop / compose down）。",
    139: "段错误（SIGSEGV）退出：进程访问了非法内存……",
    134: "收到 SIGABRT 后退出：……",
    1:   "应用自身以错误码 1 退出：通常是启动阶段的配置错误、依赖连不上，或代码抛了未捕获异常。",
    0:   "进程正常退出（退出码 0）：对常驻服务来说意味着主进程干完活就结束了……",
}
```

取退出码有两级来源：优先 `inspect` 的 `State.ExitCode`（准确），
取不到再从 `Status` 文本里正则 `Exited \((\d{1,3})\)` 抠（兜底）。

同时把 `OOMKilled=true` 和 `RestartCount>0` 也带进证据 ——
这三个值在 `/containers/json` 里**都没有**，只能通过 inspect 拿。

#### inspect 的代价要明说

一次启动分析最多额外查 **6** 个未运行容器（`_MAX_INSPECT`），
超出时报告里写清楚：

```
! 已停止的容器较多，只额外查询了前 6 个的退出码（共 9 个）。
```

理由写在代码注释里：这几次请求是额外开销，而退出码只是线索，不值得为它把响应拖长。
但"只查了 6 个"这件事必须让用户知道，否则会以为全查过了。

### 3.5 "已证实 / 推测" 做成结构性约束

需求第 3 条要求"严格区分已证实事实与推测"。靠提示词要求模型自觉是不可靠的，
所以**由渲染函数强制**（`_render_findings()`）：

```python
block = [f"{index}. [{finding.severity}] {finding.category}"]
block.append(f"   【已证实】证据：{finding.evidence[0]}")
for extra in finding.evidence[1:]:
    block.append(f"                 {extra}")
block.append(f"   【推测】可能原因：{finding.hint}")
block.append(f"   处理建议：{finding.advice}")
```

对应到数据结构，就是 `ConfigFinding` 的字段语义被固定：

```python
@dataclass(frozen=True)
class ConfigFinding:
    name: str        # 英文标识（便于写测试和去重）
    category: str    # 展示给用户的中文分类
    severity: str    # 严重 / 警告 / 提示
    evidence: tuple[str, ...]  # 具体证据（必须来自真实解析结果）
    hint: str        # 可能原因  → 永远打在【推测】后面
    advice: str      # 处理建议
```

写代码的时候就分好了：`evidence` 里只能放解析出来的东西，
`hint` 里放的才是因果推理。模型拿到的报告文本天然带着这两个标签，
它要做的只是转述。

**实测输出印证了这一点**：

```
1. [警告] 必需配置为空
   【已证实】证据：backend/.env 里这些键的值是空的：OPS_ALLOWED_HOSTS、OPS_LOG_CONTAINERS、OPS_REQUIRED_ENV
   【推测】可能原因：键存在但值为空，和「完全没配」在多数框架里是同一个结果。
   处理建议：确认是否有意留空；否则补上正确值。
```

### 3.6 安全：路径与文件范围

**路径安全**直接复用第一个魔改的 `_resolve_allowed_path()` —— 先 `resolve()`
再做包含判断，`../../etc` 和指向外部的符号链接都会在解析后被拒掉：

```
【配置检查】/ops/projects/AgentHub
总体状态：已拒绝
原因：路径不在允许检查的范围内，已拒绝：/ops/projects/AgentHub
允许的根目录（OPS_PROJECT_ROOTS）：/ops/projects
```

**文件访问范围**是这次新加的一层。配置检查天然要遍历目录，如果不设限就变成了
通用文件浏览器。三重限制：

```python
_DOTENV_NAME_RE  = re.compile(r"^(?:\.env(?:\.[A-Za-z0-9_.-]+)?|[A-Za-z0-9_.-]+\.env)$")
_COMPOSE_NAME_RE = re.compile(r"^(?:docker-compose|compose)\.ya?ml$", re.IGNORECASE)
_GITIGNORE_NAME  = ".gitignore"

_MAX_CONFIG_DIRS  = 16   # 最多扫描几个子目录（含根目录）
_MAX_CONFIG_FILES = 32   # 最多读取几个配置文件
_MAX_VALUE_PREVIEW = 10  # 每个文件最多预览几个非密钥变量的值
```

1. **文件名白名单**：只认 `.env*` / `*.env` / `docker-compose*.yml` / `compose*.yml` / `.gitignore`。
   哪怕目录里放着 `id_rsa` 也不会被读。
2. **只往下走一层**：AgentHub 这类仓库把 `.env` 放在 `backend/`、`frontend/`，
   再深就跑到 `node_modules` 去了。以 `.` / `_` 开头的目录和 `_SKIP_DIRS` 直接跳过。
3. **单文件大小上限**：默认 256 KB（`OPS_CONFIG_MAX_FILE_KB`，范围 8–4096）。
   超限就跳过并说明原因：

   ```
   ! .env：文件 20.0 KB，超过 8.0 KB 的读取上限，已跳过。配置文件正常只有几 KB，异常大的多半不是配置文件。
   ```

**编码问题不静默处理**。Windows 上用记事本把 `.env` 另存成 GBK 是真实会发生的，
读出来是乱码或直接解析失败，而且很难查：

```
! .env：不是合法的 UTF-8 编码（已用替代字符解码）。服务按 UTF-8 读取时会得到乱码，或直接解析失败。
```

### 3.7 运维声明的必需变量：`OPS_REQUIRED_ENV`

"哪些环境变量是必需的"这件事，**工具不猜**。新增配置项：

```python
OPS_REQUIRED_ENV: str = ""                                        # 逗号分隔，留空 = 不做这项检查
OPS_CONFIG_MAX_FILE_KB: int = Field(default=256, ge=8, le=4096)   # 单文件大小上限
OPS_CONFIG_MAX_OUTPUT_CHARS: int = Field(default=6000, ge=1000, le=30000)
```

判定范围是**整个项目里所有 dotenv 文件的并集** —— 一个键写在 `backend/.env`
还是 `frontend/.env` 都算配了。不然 `API_BASE_URL` 这种跨目录的键会误报。

### 3.8 一个真实的坑：Compose 插值不认 `env_file`

写这个功能时踩到的、也写进检查项的一个坑：

**Compose 的 `${VAR}` 插值发生在读取 compose 文件的那一刻，它只查两处：
compose 同级目录的 `.env` 和 shell 环境变量 —— 不查 `env_file` 指的文件。**

实测原文（`docker compose config`，`svc/.env` 里写了 `TAG=v1.2.3` / `MY_TOKEN=abc`）：

```

level=warning msg="The \"MY_TOKEN\" variable is not set. Defaulting to a blank string."
name: compose-interp-demo
services:
  app:
    environment:
      MY_TOKEN: abc      # ← env_file 确实注入进来了
      TAG: v1.2.3        # ← 同上
      TOK: ""            # ← 但 ${MY_TOKEN} 插值阶段就已经是空的
    image: 'myapp:'      # ← 镜像名被截断成 myapp:
```

镜像名变成 `myapp:` 这种"看起来正常"的值，报错位置和真正的原因离得很远。
所以 `_check_compose_interpolation()` 专门检查它，并在 `hint` 里点名这个坑：

```python
"注意：服务里 env_file 指定的文件**不参与** compose 变量插值，只认同级 .env。"
```

## 七、实际修复的 Bug

### Bug 1：启动分析把自己的容器当成"端口占用者"（真实项目上会误报）

**发现方式**：写单元测试时构造了"db 服务映射 5432，而 agenthub-db 容器正持有 5432"
这个场景，发现它被报成了端口冲突。

**原因**：判断"这个端口是不是自己人占的"时，拿**服务名**去比对：

```python
own_names = {s.name for s in compose.services.values()}          # {"db"}
if holder and holder not in own_names and not holder.endswith(
    tuple(f"-{n}-1" for n in own_names)                           # ("-db-1",)
):
```

`holder` 是容器名 `agenthub-db`，既不等于 `db`，也不以 `-db-1` 结尾 ——
两个条件都成立，于是误报。

**这不是理论问题**：真实的 AgentHub 根 compose 里 `db` 服务写着
`container_name: agenthub-db` + `ports: ["5432:5432"]`，
而容器 `agenthub-db` 确实持有宿主机 5432。
**修复前，每次对真实仓库跑启动分析都会稳定误报一条严重问题。**

**修复**：拿服务**实际匹配到的容器名**去比对：

```python
# 判断"是不是自己人"要用服务**实际匹配到的容器名**，不能拿服务名去比 ——
# 服务叫 db、容器叫 agenthub-db 的情况太常见了，用服务名比会天天误报。
own_containers = {
    container_name_of(container)
    for service in compose.services.values()
    if (container := match_container(service, containers)) is not None
}
```

修复后对真实仓库重跑，报告干净了（见 6.2）。

### Bug 2（第二个魔改遗留）：测试断言写死了工具总数

`test_log_tools.py` 里：

```python
assert len(OPS_TOOLS) == 4
```

加两个工具就红。改成断言前 4 个的顺序前缀：

```python
assert [t.name for t in OPS_TOOLS[:4]] == [
    "check_project", "check_docker", "check_service", "check_container_logs",
]
```

教训：断言"总数"的测试是维护负担，断言"包含关系"或"前缀"才有信息量。

## 九、已知限制

工具自己在报告里会主动列出"未检查"的部分（`_CONFIG_NOT_CHECKED`），
这是设计的一部分 —— 避免让模型把"没查"当成"查过没问题"：

1. **不检查配置文件内容的业务语义**。工具能发现 `POSTGRES_HOST=localhost`
   和 `POSTGRES_HOST=db` 不一样，但不知道在容器里哪个才对
   —— 那需要知道部署拓扑。
2. **不解析源码**，不知道代码里实际读了哪些环境变量。
   "必需配置"只能靠两份 `.env` 的差异 + 运维声明的 `OPS_REQUIRED_ENV` 推断。
3. **不 exec 进容器**，看不到运行中的容器实际拿到了什么环境变量
   —— 这是刻意的安全边界（只读工具不该有 exec 能力）。
4. **只看得到容器占用的宿主机端口**。宿主机上被 nginx、systemd 等非 Docker
   进程占用的端口，工具发现不了，"端口冲突"可能漏报。
   交叉验证的办法是用 `check_service` 探端口，或者人工 `netstat`。
5. **只分析根目录那一份 compose**。仓库里有 `backend/docker-compose.yml`、
   `frontend/docker-compose.yml` 等多份时，只取根目录的
   （根目录那份是主入口）。子目录里的 compose 只会被 `check_config`
   当成普通文本做静态检查，不会被拿来和容器状态比对。
6. **只往下扫一层目录**，更深的配置文件看不见。这是范围和性能的权衡：
   AgentHub 这类仓库的 `.env` 就在 `backend/`、`frontend/` 这一层。
7. **不做跨机器比对**。工具看到的是本机 Docker，`compose` 文件里写的
   宿主机路径在这台机器上不存在时只报"构建目录不存在"，
   不知道是不是别的机器上部署的配置。
8. **PyYAML 是新增的显式依赖**（`PyYAML==6.0.3`）。原先它只是
   `langchain-community` 等包的间接依赖，能 import 到纯属运气；
   `config_check.py` 里有 `YAML_AVAILABLE` 兜底（缺了会给一句中文说明
   而不是崩），但功能上确实需要它，所以写进了 `requirements.txt`。
9. **单文件 256 KB / 32 个文件 / 16 个目录**的上限是硬编码常量，
   不通过环境变量暴露。真遇到超大配置的项目，需要改代码。
